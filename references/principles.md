## 1. 整洁代码意味着什么

不同大师的定义指向同一组特质：

- **可读性**：代码是写给人读的。机器不在乎，人在乎；而人只在乎"改起来是否安全"。
- **无重复**：重复是糟糕设计的根源，也是"改一处漏一处"的来源。
- **单一职责**：一个模块/函数/类只解决一个问题。
- **有测试**：没有测试的代码不敢改，不敢改的代码就会腐烂。
- **表达力**：命名准确、结构清晰，读代码不需要读注释或猜。

**判断标准（好用的一句）**：如果你要向同事解释这段代码，需要说"它其实还顺便做了……"，那它就不整洁。

**重要提醒**：整洁不是"漂亮"，而是"可安全修改"。不要用审美偏好替代工程判断。

## 2. 有意义的命名

| 规则 | 差的例子 | 好的例子 |
|---|---|---|
| 名副其实：名字说明为什么存在、做什么、怎么用 | `int d; // 消逝的天数` | `int daysSinceCreation` |
| 避免误导 | `accountList`（实际是数组/Map） | `accounts` / `accountMap` |
| 做有意义的区分 | `ProductInfo` vs `ProductData`、`a1/a2` | `Product` / `ProductSnapshot` |
| 用可读、可搜索的名字 | `7`、`e`、`genymdhms` | `MAX_CLASSES_PER_STUDENT`、`elapsedTimeInDays` |
| 避免编码前缀/匈牙利命名 | `strName`、`m_dsc`、`iCount` | `name`、`description`、`count` |
| 类名用名词，方法名用动词 | `class Data`、`method handle()` | `class Customer`、`method save()` |
| 每个概念一个词，别混用同义词 | 同时用 `fetch`/`retrieve`/`get` | 统一用 `get`（或统一用 `fetch`） |
| 用领域术语（解决方案域/问题域），别用自创黑话 | `theThing`、`magicFlag` | `pendingOrder`、`isRetryable` |
| 长度与作用域成正比 | 全局变量 `x` | 局部循环变量 `i` 可以短，全局配置要完整 |
| 加有意义的上下文 | 一堆 `state`、`street` 散落 | `addrState`、`addrStreet`（或收进 Address 对象） |
| 别留废话/双重含义 | 多余语境 `GasStationDeluxe`，函数里的 `NameString` | 去掉冗余前缀 |

**判定技巧**：把命名当成注释的替代品。如果你需要写 `// 检查是否可重试`，那个函数就该叫 `isRetryable()`。

**反例警告**：改名不是"个人喜好"。名字误导会导致真实的 bug——`isValid` 返回 null、`getUsers` 会写数据库，这类问题比格式严重得多。审查时把误导性命名当作 Major 甚至 Blocker。

## 3. 函数

**规则：**

1. **短小**。经验值：20 行以内、缩进不超过 2 层。不是硬性上限，而是信号——超出通常说明它做了多件事。
2. **只做一件事 (Do one thing)**。判定标准：**能否从中抽出一个不再是"单纯重述实现"的函数**。能抽，就说明它不止一件事。另一个判定：描述它需要"并且"。
3. **每个函数一个抽象层级**。不要在同一个函数里混用高层业务表达（`renderPage()`、`createOrder()`）和低层细节（`s = s.substring(1)`、字符串拼接、下标运算）。
4. **自顶向下阅读**：代码应该像一组"如何做"的段落，越往下细节越多。
5. **switch/if-else 链要警惕**：只会出现一次、用于创建多态的 switch 可以接受；重复出现的同类 switch 应该用多态或表驱动替换（见重构手册）。
6. **参数越少越好**：0 个最好，1–2 个常见，3 个已是上限；超过就抽**参数对象**。布尔参数是坏味道——它几乎总是在说"这个函数做两件事"。
7. **避免输出参数与副作用**：不要 `appendFooter(report)` 这种靠改入参返回结果的写法。副作用是"意外的状态变更"，哪怕叫 `checkPassword` 也不该顺便初始化 session。
8. **命令查询分离**：要么改变状态、返回 void；要么查询状态、返回结果。不要既改又返回。
9. **抽离 try/catch**：错误处理是"一件事"，把它整块抽成独立函数，主流程才干净。
10. **不要重复自己 (DRY)**：重复是函数抽取的最强动机。
11. **别怕多写小函数**：小函数多不是问题，名字本身就是文档和分层结构。

**改法示例：**

```text
// 差：混合抽象层级 + 多个职责 + 副作用
void render(PageData page, boolean isSuite) {
  // 一大段 HTML 拼接、字符串下标、计算、写文件、日志……
}

// 好：每个函数一个抽象层级
void render(PageData page, boolean isSuite) {
  buffer = createBuffer()
  path = buildPagePath(page, isSuite)
  writePage(buffer, path)
  logRender(path)
}
```

**误区**：不要为了"行数达标"把一行代码拆成函数；也不要把只调用一次的代码段硬抽成 `handleStep1()`/`handleStep2()` 这种无信息名的碎片。抽出的函数必须**有一个能说清意图的好名字**，否则不抽。

## 4. 注释

**核心观点**：注释是必要的恶。它的存在往往说明我们没能用代码表达意图。**能靠改名/抽函数消除的注释，优先消除。**

**值得写的注释：**

- **法律/版权信息**。
- **提供信息的注释**：解释无法用代码表达的意图，如正则或位运算的作用。
- **对意图的解释**：为什么用这个算法/这个阈值，而不是另一个。
- **阐释**：把晦涩的第三方/标准库用法翻译成可读说明。
- **警告后果**：`// 这个测试跑起来要 10 分钟，除非改核心逻辑否则别改`。
- **TODO / FIXME**：可以，但要定期清理，并写清为什么和什么条件下处理。
- **放大重要性**：某段代码看似无关紧要但极其关键。
- **javadoc/公共 API 文档**：对外接口值得写清楚契约、参数、异常、副作用。
- **文档化第三方行为**：尤其是没文档或行为反直觉的库。

**坏注释（见到就删或改）：**

- 喃喃自语的碎碎念、只对作者有意义的笔记。
- **冗余注释**：复述代码在做什么（`// 自增 i`）。
- **误导性注释**：比不写注释更糟，会让读者建立错误模型。过期的注释属于此类。
- **日志式注释**：`// 2011-03-12 改成这样 // 2012-01-05 又改回去`——那是版本控制工具的活。
- **注释掉的代码**：这是最讨厌的一类。**直接删**，版本控制会保留历史（真需要就留一句说明为什么删/在哪能找回）。
- **能用函数或变量名替代的注释**。
- **归属于函数/类的注释**：版权头、作者、变更记录不该堆在类顶部。
- **关闭日志的注释**、**噪声注释**（`/** The name. */ private String name;`）。
- **别用注释为烂代码辩解**。把代码改好，然后删掉注释。
- **别在注释里写非本地信息**：如把构建步骤、部署说明塞进源码注释——那属于 README。

**判定技巧**：读代码时如果发现"注释说得比代码清楚"，说明代码该改；如果发现"注释和代码不一致"，**注释是错的，或者代码已经变了**——这两种情况都要立刻处理。

## 5. 格式

- **格式的目的是沟通**，不是审美。**项目一致性 > 个人偏好**：先看仓库里的 formatter/linter 配置和周围文件的风格。
- **垂直格式**：文件不宜过长（经验值几百行以内，超过说明可能承担了多个职责）；**相关代码要靠近**——变量声明贴近使用处，调用者和被调用者尽量靠近（自顶向下）。
- **垂直距离表达关联强度**：概念相关的东西不该隔着一堆无关代码；不相关的东西不该挤在一起。
- **垂直顺序**：被调用者放在调用者下方，读起来像报纸文章（标题 → 概要 → 细节）。
- **横向格式**：行不宜过长；用空格表达结合紧密程度（`a*b + c*d`）；不要无意义对齐；缩进表达层级，**不要用缩进撒谎**（同一函数里的语句该在同一层级）。
- **团队规则优先**：如果项目用 gofmt/black/prettier，你的所有排版意见都应让位——**不要在 review 里争论 formatter 能解决的问题**。

## 6. 对象与数据结构

**关键区分：**

- **对象**：暴露行为，隐藏数据（内部结构可随时替换，调用方不受影响）。
- **数据结构**：暴露数据，没有行为（就是一组字段的容器，如 DTO、配置结构）。

**过程式 vs 面向对象是相反的取舍**：加新函数容易、加新类型难（过程式）；加新类型容易、加新函数难（面向对象）。不要两者都想占。

**要避免的坏味道：**

- **混合体 (hybrid)**：一半对象一半数据结构——既有 getter/setter 暴露所有字段，又含业务逻辑。**最坏的结构**，因为它同时放弃了两种好处。
- **得墨忒耳定律 (Law of Demeter)**：方法只应调用：自己、自己的字段、自己创建的对象、传入的参数。`a.getB().getC().doSomething()` 是"火车残骸"，说明调用方知道了太多内部结构；改成 `a.doSomething()`，让 a 自己处理。
- **暴露内部结构**：返回可变内部集合（`getList()` 直接返回内部 list）会破坏封装，改成返回不可变视图或副本。
- **数据/对象反对称性**：别给数据结构硬塞行为，也别到处扒对象的字段。

## 7. 错误处理

**规则：**

1. **用异常，不要返回错误码/错误字符串**。错误码污染调用链、迫使调用方立即判断、容易忘记检查；异常把正常路径和错误路径分开。
2. **先写 try-catch-finally**。把可能失败的部分圈起来，用异常定义事务范围；主逻辑从 try 的第一行开始。
3. **用异常提供上下文**：异常消息要包含失败的操作和关键值（哪个文件、哪个 ID、为什么），别只抛 `new Error("failed")`。调用方需要足够信息判断怎么处理。
4. **按调用方需要定义异常类**：包一层第三方异常（`throw new PortDeviceFailure(e)`），避免外部库的异常类型扩散到你的业务代码里。
5. **别返回 null，别传 null**。返回 null 等于给每个调用方埋一颗雷；改为返回空集合、空对象、Optional，或者抛异常。外部 API 返回 null 时用包装层挡住。
6. **不要用异常做流程控制**，也不要用 `if` 检查代替异常（除非是真正的边界校验）。
7. **不要吞异常**：空的 catch 块和 `catch (e) { /* ignore */ }` 是最危险的模式——至少记录、至少重新抛出有意义的信息。
8. **不要在 finally 里 return / 抛异常**，会吞掉原异常。
9. **失败要快速暴露**：宁可启动时崩溃，也不要带着错误状态继续跑。
10. **清理资源用语言提供的机制**：try-with-resources / `with` / `defer` / `using`。

**示例：**

```text
// 差：返回码 + 吞异常 + null 传播
int deletePage(Page page) { if (page == null) return -1; try { ... return 0 } catch (e) { return -1 } }

// 好：异常 + 上下文 + 单一职责
void delete(Page page) {
  try { deletePageAndAllReferences(page) }
  catch (Exception e) { logError(e); throw new DeletionFailure(page.name, e) }
}
```

## 8. 边界

- **第三方代码要隔离**：不要把第三方 API 直接散布到业务逻辑里。用包装/适配层（Adapter、Facade）集中管理，将来换库或升级只改一处。
- **学习型测试 (learning test)**：对第三方行为不确定时，写测试记录它的真实行为（不是你以为的行为）。这既能验证理解，也能在升级第三方时立刻发现行为变化。
- **边界代码要有明确的所有权**：谁负责包装、谁负责跟进第三方升级，要清楚。
- **别让"还没实现"的第三方接口污染你的设计**：宁可自己定义一个干净的接口，再写适配器对接。
- **对不确定的边界留出统一入口**：日志、错误转换、重试策略放在边界层，不要散落各处。

## 9. 单元测试

**三条定律（TDD）**：在写不出失败的测试前，不写生产代码；在写不出失败的测试前，不写更多测试；只写刚好让当前测试通过的生产代码。

**测试的整洁性同等重要**：测试代码和产品代码一样需要维护。测试变脏的代价是——你不再敢改测试，进而不再敢改产品代码。

**F.I.R.S.T 原则：**

- **Fast（快）**：慢测试没人愿意跑，也就不会跑。
- **Independent（独立）**：测试之间不依赖执行顺序、不共享可变状态。
- **Repeatable（可重复）**：任何环境、任何时间都能跑出相同结果（不依赖网络、真实时钟、随机数）。
- **Self-Validating（自验证）**：结果只有通过/失败，不需要人看日志判断。
- **Timely（及时）**：在生产代码之前写（至少同一个提交里）。

**每个测试一个概念**：一个测试里出现多组"构造-操作-断言"，通常应拆成多个测试，名字才说得清到底验证什么。

**好的测试结构：构造-操作-断言（Build-Operate-Check）**，最好用 Given-When-Then 或 Arrange-Act-Assert 明确分开。

**测试坏味道：**

- 双重标准：产品代码要求整洁，测试代码随便写（重复、魔法值、命名含糊）。
- 含糊的测试名：`test1`、`testWorks`。测试名应该说清"在什么条件下、期望什么"。
- 断言散乱、断言太多、把断言藏在辅助函数深处。
- 测试之间互相依赖（依赖执行顺序、共享 fixture 被改坏）。
- 用 sleep 等待异步结果，而不是用可控的时钟/事件。
- 为了通过而修改断言、跳过测试、注释掉测试。

**覆盖率的正确理解**：覆盖率是"没被覆盖的代码没有测试"的提示，不是质量分数。不要为了数字写没有断言的测试。

## 10. 类

- **类要小**：不是按行数（虽然行数也是信号），而是按**职责数量**。
- **单一职责原则 (SRP)**：一个类应该只有一个引起它变化的原因。**判定技巧：能否用"并且"描述它**——"这个类负责订单计算**并且**负责订单持久化"→ 拆。另一个技巧：说出类名后，能用 25 个词以内描述它的职责而不出现"并且/或者"。
- **高内聚 (Cohesion)**：类里字段被方法共享的程度。每个方法都用上所有字段 → 最大内聚。出现"只给少数方法用、互相不共享字段"的字段簇 → 说明这个类该拆成几个类。
- **为修改而组织 (OCP/DIP)**：类应该对扩展开放、对修改封闭。新功能来了，理想情况是"加新类"而不是"改旧类里的一堆 if"。依赖抽象（接口）而不是具体实现，隔离变化。
- **避免上帝类 (God Class)**：几千行、几十个 public 方法、被所有模块依赖的类，是维护灾难。按职责和变化原因切开。
- **类名要准确描述职责**：`Processor`、`Manager`、`Util`、`Helper` 这类名字往往暴露了职责不清。
- **隔离变化点**：把易变的实现细节（第三方、格式、协议）藏在稳定接口后面。

## 11. 系统

- **构造与使用分离**：对象该在哪里 `new`，和它在哪里被用，是两件事。用依赖注入、工厂、抽象工厂把"构建"搬到启动/装配层（main、容器、配置模块）。业务代码只声明它需要什么。
- **横切关注点用切面/中间件**：日志、事务、安全、缓存等跨越多个模块的关注点，不要复制粘贴进每个业务函数；用装饰器、中间件、AOP。
- **用代理/装饰器扩展系统**，而不是改核心代码。
- **测试驱动系统架构**：如果某个设计难以测试，通常是耦合太紧——这是架构信号。
- **延迟决策**：在有足够信息之前不要锁定架构（框架、数据库、协议）。用 POJO/纯函数保持核心逻辑与基础设施解耦。
- **标准要显眼**：项目用什么语言、什么框架、什么规范，应该一眼可查（README/文档/模板），而不是口口相传。
- **领域特定语言 (DSL)**：适度的 DSL（如测试里的构建器、业务规则表）能让意图更清晰，但别为了优雅造一门没人会用的语言。

## 12. 迭进：简单设计四原则

按**优先级顺序**应用（Kent Beck 的简单设计）：

1. **跑通所有测试**。不能验证的系统不值得谈结构。
2. **消除重复**。重复是主要的设计腐化来源。重复包括：完全相同的代码、相似的结构、重复的算法、重复的判断链。
3. **表达意图**。好名字、良好的函数/类划分、标准术语、清晰的测试名。让读者不需要问"这是什么意思"。
4. **最少量的类和方法的数量**。在不损害前三条的前提下，不做无谓的抽象。

第 4 条是最容易被忽略也最常被违背的：**不要提前抽象**。三行相似代码好过一个错误的抽象。

**Rule of Three**：第一次照写，第二次心里记一下，第三次出现时才抽象。

**"简洁"不等于"少"**：该有的分层和命名要加；该省的多余间接层要省。判断标准仍是可读性。

## 13. 并发编程

并发是解耦"做什么"和"何时做"，代价是复杂度与不确定性。

**原则：**

- **单一职责**：并发相关的代码应该单独成类/模块，本身"只做一件事"（管理并发）。业务逻辑不应关心线程。
- **限制数据作用域**：能传副本就不共享；共享数据越少，同步需求越少。
- **使用线程安全的集合/原语**，但要知道它保护的是单个操作还是复合操作（`check-then-act` 仍需外部同步）。
- **使用数据副本**：多条线程读写同一对象是主要 bug 来源。
- **线程尽可能独立**：每个线程自己处理自己的数据/文件/连接，减少交互。
- **知道你的库/框架是否线程安全**：Servlet、Spring bean、React 组件、静态工具类的线程模型要清楚。
- **保持同步区域最小**：锁里不做 I/O、不做长耗时计算；不要在锁内调用外部回调（可能死锁）。
- **避免死锁**：统一加锁顺序；用超时锁；避免嵌套锁。
- **不自己管理线程生命周期**：用线程池/执行器/协程调度器，避免手动 `new Thread` 与 `sleep`。
- **并发 bug 靠测试暴露**：写可复现的并发测试、压力测试、把系统跑在多于一个 CPU 上；添加 `jiggling`（随机延迟/交错）来提高复现率。**并发代码"看起来对"毫无意义。**
- **先保证单线程正确**，再考虑并发；能不用共享可变状态就不用。
- **谨慎使用 eager/懒加载**：懒初始化的双重检查锁容易写错，优先用语言提供的安全构造（`once`、`Lazy<T>`、`synchronized` 方法、模块级不可变初始化）。
