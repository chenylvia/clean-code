# 安全重构手册

重构 = **在不改变外部行为的前提下改善内部结构**。行为变了，那就是改功能，应该分开做、分开提交、分开审查。

## 一、开始前的安全网

**没有安全网就大改，是把重构变成赌博。** 按顺序尝试：

1. **已有测试**：先跑一遍，确认全绿。如果原本就是红的，先弄清楚哪些红是"已知问题"，别把既有失败算到自己头上。
2. **没有测试** → 写 **characterization test（特征测试）**：不是验证"应该怎样"，而是**记录现在实际怎样**，包括看起来像 bug 的行为。目的是"改完之后行为没变"，而不是"证明现在是对的"。把发现的可疑行为记录下来，之后单独问用户。
3. **完全无法测试**（硬编码依赖、静态调用、难构造的对象）→ 先做**接缝 (seam) 处理**：把难测的依赖抽到可替换的位置（提取方法、提取接口、参数化构造），这一步本身是重构，要单独提交。
4. **都没有** → 至少确认一份可复现的手工验证步骤，并明确告诉用户："没有自动化测试，我按以下步骤手工验证了 X，Y 部分无法验证。" 不要假装安全。

**版本控制是最后的安全网**：每完成一个小步就提交，保证能回滚。改动越大，提交越要碎。

## 二、重构的节奏

1. **一次只做一种改动**。重命名、抽函数、移动代码、内联——不要在同一步里混合。
2. **每步验证**：跑测试 / 编译 / 类型检查 / lint。全绿再进下一步。红了就立刻回到上一步（回滚而不是往前修）。
3. **小步提交**：每次提交是一个完整、可回滚、行为不变的改动单元；提交信息说明"做了什么结构改动，行为未变"。
4. **重构与功能变更分离**：同一个 PR 里既重构又加功能，审查者无法区分"行为变了"和"结构变了"，出问题也无法二分定位。如果必须同 PR，用交替提交（重构提交 → 功能提交）并在描述里标明。
5. **TDD 的第三步**：红 → 绿 → **重构**。让测试通过时可以脏，通过之后立刻清理。
6. **保持可工作状态**：任何时刻主干代码都能编译、都能跑。不要留一个"下午就修好"的中间态。
7. **先测行为，再动结构**：重构中如果发现真实缺陷，**不要顺手修**——记下来，重构完成后再单独作为一个 bug 修复（附测试）。

## 三、味道 → 手法映射

| 观察到的味道 | 首选手法 |
|---|---|
| 名字看不出意图、误导 | 重命名（Rename）、拆分为多个变量/函数 |
| 函数过长、混合抽象层级 | 提取函数（Extract Function）、卫语句、拆分阶段 |
| 一段代码需要注释才能看懂 | 提取函数并用注释意图命名，然后删注释 |
| 复杂布尔表达式 | 提取变量、封装条件为判定函数 |
| 深层嵌套 if/else | 卫语句（提前返回）、用多态/策略替代条件 |
| 参数过多 | 引入参数对象、用构建器、拆分函数 |
| 布尔标志参数 | 拆成两个函数、用多态/枚举替代 |
| 同类 if/switch 反复出现 | 多态、策略、表驱动 |
| 重复代码块（第三处出现） | 提取函数/类，上移共享代码 |
| 循环里做多件事 | 拆分循环（Split Loop）、拆分阶段（Split Phase） |
| 方法依赖别的对象的数据 | 移动函数（Move Method）到数据所在的类 |
| 类字段分成互不相关的簇 | 提取类（Extract Class） |
| 一个类什么都管 | 提取类 + 按变化原因切分 |
| 调用链 `a.getB().getC()` | 隐藏委托（Hide Delegate）、加转发方法 |
| 暴露内部集合/字段 | 封装集合、封装字段 |
| 返回 null 到处判断 | 空对象（Null Object）、Optional、空集合、抛异常 |
| 错误码/错误字符串满天飞 | 用异常替代返回码、定义领域异常 |
| 继承只为复用几行代码 | 用组合替代继承 |
| 难以测试（依赖写死） | 提取接口 + 依赖注入、参数化构造 |
| 时序耦合隐式存在 | 模板方法、构建器、单一入口 |
| 魔法数字/字符串 | 命名常量、枚举 |
| 过长的构造函数 | 构建器（Builder）或工厂函数 |
| 构造函数里有复杂逻辑 | 提取工厂函数、静态创建方法 |

## 四、常用手法详解

每条都遵循"小步 + 每步验证"。

### 重命名 (Rename)
- **何时**：名字不表达意图、有歧义、与领域术语不一致。
- **怎么做**：用 IDE 的重命名功能（不要手改字符串）；一次只改一个概念；如果一个名字改不动（比如它承担了两种职责），说明该先拆函数。
- **注意**：改名会改变公开 API/序列化字段/反射引用时，要先确认影响面。

### 提取函数 (Extract Function)
- **何时**：函数过长、有需要注释才懂的片段、代码被复制、混合抽象层级。
- **怎么做**：选一段**语义完整**的语句块 → 抽成函数 → **给它一个表达意图的名字**（如果需要"并且"来描述，说明该抽成两个函数）→ 用参数传递所需数据，尽量用返回值而不是输出参数。
- **注意**：抽出的函数必须有信息量高的名字，否则是噪声；不要抽出只有一行、名字比实现还长的碎片。

### 内联 (Inline)
- **何时**：函数体比函数名还清楚、无意义的转发函数、过度抽象带来的间接层。
- **注意**：内联是纠正"过早抽象"的主要手段。**抽象的代价是间接层**，只在它换来可读性或复用时才值。

### 引入解释性变量 / 查询替代临时变量
- **何时**：表达式复杂、临时变量含义不清。
- **怎么做**：`if (a > 3 && b < 7)` → `const isEligible = ...; if (isEligible)`；把只算一次的中间变量换成明确命名的查询函数。

### 卫语句替代嵌套 (Replace Nested Conditional with Guard Clauses)
- **何时**：if 嵌套多层、异常路径被埋在深处。
- **怎么做**：把"异常/边界情况"提到函数开头提前返回，主逻辑保持在同一缩进层级。

### 用多态/策略/表驱动替代条件
- **何时**：同一组类型判断在多处重复；新增类型要改多个 switch。
- **怎么做**：把每种分支的行为搬到独立类/函数 → 用一个映射或工厂选择实现 → 调用方只调用统一接口。
- **注意**：只出现一次、简单、稳定的条件不值得引入多态——那是过度设计。

### 拆分循环 / 拆分阶段
- **何时**：一个循环里做了多件不相关的事（计算 + 输出 + 校验）；一段代码混合多个阶段的逻辑。
- **怎么做**：拆成多个独立循环/阶段，中间用明确的数据结构传递；性能敏感时先测量再决定。

### 移动函数 / 移动字段 / 提取类
- **何时**：特性依恋（方法更关心别的类的数据）、类字段分成不相关的簇、类承担多个变化原因。
- **怎么做**：把数据和行为放到一起；提取类后检查内聚性是否提高（每个方法是否用到了大部分字段）。

### 隐藏委托 / 移除中间人
- **何时**：调用方需要 `a.getB().getC()` 才能办事（隐藏委托）；或者一个类几乎所有方法都只是转发（移除中间人）。
- **注意**：两者方向相反，取决于"封装"和"便利"哪个更重要。频繁变化的内部结构要封装；稳定的转发层可以移除。

### 封装字段 / 封装集合
- **何时**：外部直接改内部状态、直接拿到内部可变集合。
- **怎么做**：改为方法暴露行为；集合返回不可变视图或副本，修改通过专门方法。

### 引入空对象 / Optional / 空集合
- **何时**：到处 `if (x != null)`；返回 null 迫使调用方防御。
- **怎么做**：返回空集合或空对象；用类型系统表达"可能不存在"；在边界层把外部 null 转成你的约定。

### 用异常替代返回码
- **何时**：错误码在调用链上层层传递与判断、错误容易被忽略。
- **怎么做**：定义领域异常，在边界层转换第三方异常，保留上下文信息。

### 用组合替代继承
- **何时**：为复用代码而继承、继承层次过深、基类依赖子类。
- **怎么做**：把可变行为抽成接口/策略并注入；只在真正"是一种"且需要多态替换时用继承。

### 提取接口 + 依赖注入（为可测试性）
- **何时**：难以测试（直接 new 具体依赖、静态调用、访问真实外部服务）。
- **怎么做**：定义最小接口表达"我需要什么" → 通过构造函数参数注入 → 测试时传替身（fake/stub）。
- **注意**：接口应表达**使用者的需求**，而不是照抄实现类的所有方法。

### 消除重复（Rule of Three）
- **何时**：同一逻辑第三次出现。
- **怎么做**：上移到共享位置。**先确认是同一个概念**——长得像但会朝不同方向变化的代码，强行合并是灾难。

## 五、遗留代码的特殊策略

遗留代码（无测试、耦合严重、没人完全懂）的重构原则：**先让它可测，再让它好看**。

- **找接缝 (Seam)**：在不修改行为的前提下能插入替换行为的位置。常见做法：提取方法、把 `new` 移到工厂、把静态调用包一层、给构造函数加参数。
- **打破依赖再测试**：目标是把代码推进测试框架，而不是一次改干净。
- **萌芽法 (Sprout Method / Sprout Class)**：不要改那段难动的老代码，而是**新写一个干净的函数/类**，在老代码里调用它。风险最低，适合没有人敢碰的核心逻辑。
- **特征测试优先**：记录现状（包括 bug），改完对比。
- **只改你要动的那部分**：童子军军规 ≠ 顺手重写整个文件。把无关部分留原样，减少 diff 和风险。
- **给关键理解写下来**：你对老代码行为的发现（尤其反直觉的部分）要写成测试或注释，否则下一个人要重新踩一遍。
- **不要大爆炸重写**：见下节。

## 六、什么时候该停

重构的目的是**让下一次改动不再痛苦**，不是追求完美结构。

停下来，当：

- 目标改动点周围的代码已经清晰、有测试、职责明确。
- 剩下的问题不影响当前任务，且改动它们会扩大风险面。
- 你已经连续几步都在"顺便"改与任务无关的代码。
- 你在为假想的未来需求加抽象。

**把没做完的部分写成明确的后续建议**（含位置和理由），交给用户决定，而不是自己一路改下去。这既尊重用户的范围控制，也让改动可审查。

## 七、常见陷阱

| 陷阱 | 为什么糟 | 正确做法 |
|---|---|---|
| 大爆炸重写 | 几个月无产出、行为难以对齐、风险巨大，且往往中途放弃 | 增量重构：strangler pattern（绞杀者模式），新旧并存逐步替换 |
| 没有测试就大改 | 出问题无法定位，等于赌博 | 先建安全网（特征测试/接缝） |
| 混合重构与功能变更 | 审查与二分定位失效 | 分开提交/分开 PR |
| 一次改太多 | diff 巨大、审查失真、回滚代价高 | 小步、每步验证 |
| 过度抽象 | 间接层增加阅读成本，规则为了"通用"而扭曲 | Rule of Three；不合成就内联回去 |
| 为指标重构 | 覆盖率/行数/lint 分数好看，但可读性没提升 | 以"下一个改它的人是否更轻松"为准 |
| 顺手修 bug | 混淆"行为不变"的前提，破坏可回滚性 | 单独记录、单独修复、附测试 |
| 静默改变公开 API/数据格式 | 影响下游，破坏兼容性 | 明确告知用户并列入风险说明 |
| 一次重命名/移动大量文件 | 破坏 git 历史可追性、review 无法进行 | 改名/移动单独成一次提交 |
| 重构到一半停下 | 主干处于半成品状态，别人无法工作 | 保持每一步都可工作；确实要停就回滚到最后一个绿状态 |

## 八、给用户的交付格式

重构任务完成后，按这个结构汇报（不要只贴一大段 diff）：

```markdown
## 重构目标与范围
<针对什么问题，改了哪些文件；明确说明未改动的部分>

## 安全网
<做了哪些测试/手工验证；哪些部分无法验证，风险是什么>

## 改动步骤
1. <第一步：做了什么手法，验证结果>
2. ...

## 行为是否改变
<默认：不变。若发现并修正了 bug，单独列出，说明原行为与新行为>

## 未处理的问题（建议后续单独做）
- `path/to/file.py:120` — <问题与理由>
```

如果用户只要求"帮我看看/给建议"，就停在建议层面，先问是否动手改。
